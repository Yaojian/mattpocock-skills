# 代码库设计（Codebase Design）

设计**深模块**：在干净的接缝上，用小接口承载大量行为，并能穿透该接口测试。凡是设计或重组代码的地方，都使用这里的语言和原则。目标是给调用方带来杠杆（leverage），给维护者带来内聚（locality），给所有人带来可测性。

## 术语表

严格使用这些术语：不要替换为“组件（component）”、“服务（service）”、“API”或“边界（boundary）”。语言一致本身就是目的。

**模块（Module）**：任何拥有接口和实现的东西。刻意与规模无关：函数、类、包或跨层的切片都可以是模块。*避免*：单元（unit）、组件（component）、服务（service）。

**接口（Interface）**：调用方为正确使用模块而必须知道的一切：类型签名，还有不变量、顺序约束、错误模式、必需配置和性能特征。*避免*：API、签名（signature，太窄，只指类型层面的表面）。

**实现（Implementation）**：模块内部的代码体。区别于**适配器（Adapter）**：一个东西可以是小适配器加大实现（例如 Postgres 仓库），也可以是大适配器加小实现（例如内存替身）。讨论接缝时用“适配器”，其他情形用“实现”。

**深度（Depth）**：接口处的杠杆。调用方（或测试）每学习一单位接口，能驱使的行为量。大量行为藏在小接口之后，就是**深（deep）**模块；接口几乎和实现一样复杂，就是**浅（shallow）**模块。

**接缝（Seam）**（出自 Michael Feathers）：一个可以不改其位置而改变其行为的地方；即模块接口所处的*位置*。接缝放哪里是独立的设计决策，区别于接缝后面放什么。*避免*：边界（boundary，与 DDD 的限界上下文重载）。

**适配器（Adapter）**：在接缝处满足接口的具体东西。描述的是*角色*（填哪个槽位），而不是实质（内部是什么）。

**杠杆（Leverage）**：调用方从深度中得到的东西。每学习一单位接口，换来更多能力。一份实现，在 N 个调用点和 M 个测试上获得回报。

**内聚（Locality）**：维护者从深度中得到的东西。改动、缺陷、知识和验证集中在一处，而不是散落在调用方各处。修一次，到处都修好。

## 深与浅

**深模块**等于小接口加大实现：

```
┌─────────────────────┐
│   Small Interface   │  ← 方法少，参数简单
├─────────────────────┤
│                     │
│  Deep Implementation│  ← 复杂逻辑藏在内部
│                     │
└─────────────────────┘
```

**浅模块**等于大接口加薄实现（应避免）：

```
┌─────────────────────────────────┐
│       Large Interface           │  ← 方法多，参数复杂
├─────────────────────────────────┤
│  Thin Implementation            │  ← 只是透传
└─────────────────────────────────┘
```

设计接口时，问自己：

- 能否减少方法数量？
- 能否简化参数？
- 能否把更多复杂性藏进去？

## 原则

- **深度是接口的属性，不是实现的属性。** 深模块内部可以由小而可模拟、可替换的部件组成；它们只是不属于接口。模块可以同时拥有**内部接缝**（实现私有，仅自家测试使用）和位于接口处的**外部接缝**。
- **删除测试。** 想象删掉该模块。如果复杂性随之消失，它就是透传；如果复杂性在 N 个调用方处重新冒出来，它就是物有所值。
- **接口就是测试面。** 调用方和测试走过同一条接缝。如果你想绕过接口去测*后面*的东西，模块的形态多半不对。
- **一个适配器意味着假设的接缝，两个适配器意味着真实的接缝。** 除非真的有东西在这条接缝两侧变化，否则不要引入接缝。

## 为可测性而设计

好的接口让测试自然而然：

1. **接受依赖，不要创建依赖。**

   ```typescript
   // 可测
   function processOrder(order, paymentGateway) {}

   // 难测
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，不要产生副作用。**

   ```typescript
   // 可测
   function calculateDiscount(cart): Discount {}

   // 难测
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **表面积小。** 方法越少，需要的测试越少；参数越少，测试准备越简单。

## 关系

- 一个**模块**恰好拥有一个**接口**（它向调用方和测试呈现的表面）。
- **深度**是**模块**的属性，相对其**接口**衡量。
- **接缝**是**模块**的**接口**所在之处。
- **适配器**位于**接缝**上，满足**接口**。
- **深度**为调用方带来**杠杆**，为维护者带来**内聚**。

## 已否决的表述

- **深度等于实现行数除以接口行数**（Ousterhout 的定义）：会奖励往实现里注水。我们采用深度即杠杆。
- **“接口”等于 TypeScript 的 `interface` 关键字或类的公有方法**：太窄，这里的接口包括调用方必须知道的每个事实。
- **“边界（Boundary）”**：与 DDD 的限界上下文重载。请说**接缝**或**接口**。
