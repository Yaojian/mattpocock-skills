# Ask Matt

你记不住每个技能，所以直接问就好。

一个**流程（flow）**是指贯穿多个技能的一条路径。大多数路径都沿着一条**主流程**展开，另有两条**入口（on-ramp）**汇入其中。其余技能要么独立存在，要么是垫在底层的一层词汇。

## 主流程：从想法到上线（idea → ship）

大多数工作都会走这条路线：你有一个想法，想把它构建出来。

1. **`/grill-with-docs`** 通过追问（interview）打磨想法。只要你在**工作目录中工作**，就从这里开始：它是有状态的（stateful），学到的内容会保留在 `CONTEXT.md` 和 ADR 中。（没有工作目录？改用 `/grill-me`，见 Standalone 一节。两者运行的是同一个 `/grilling` 原语（primitive）；`grill-with-docs` 会留下书面记录，只要有仓库可以承载这些记录，它就是两者中更好的选择。）
2. **分支：能否在对话中解决所有问题？** 如果某个问题需要可运行的答案（状态、业务逻辑、必须亲眼看到的 UI），就先绕道做原型，并由 **`/handoff`** 在两个方向上衔接（原型位于独立目录中，而这正是 `/handoff` 的用途；见阶段边界一节）：
   - 用 **`/handoff`** 输出交接文件，然后基于该文件开启一个全新会话，
   - 用 **`/prototype`** 以一次性代码回答该问题，
   - 再用 **`/handoff`** 把学到的东西传回去，并在最初的想法主线中引用它。
3. **分支：这是需要多个会话的构建吗？**
   - **是** → **`/to-spec`**（把讨论主线整理成规格说明），然后用 **`/to-tickets`** 拆分为示踪弹（tracer bullet）工单，每个工单声明各自的**阻塞边（blocking edge）**。在本地问题跟踪器上，就是 `.scratch/<feature>/issues/` 下每个工单一个文件，按阻塞优先的顺序手动推进；在正式的问题跟踪器上，这些边会成为原生的阻塞链接，因此阻塞项已完成的工单都可以直接领取：每个工单启动一次 **`/implement`**，**在每个工单之间用 `/clear` 清空上下文**。每个工单都是自包含的，因此最后一个工单的上下文可以直接丢弃。
   - **否** → 直接在这里、在同一个上下文窗口中运行 **`/implement`**。

   无论走哪条路，**`/implement`** 都会在内部驱动 **`/tdd`** 构建每个问题（一次完成一个红绿切片），提交前再运行 **`/code-review`**，对差异做双轴评审（Standards 加 Spec），然后收尾。如果你只想在没有完整规格说明的情况下，用测试先行的方式构建一个具体行为，就单独使用 **`/tdd`**；如果你想对照某个固定点评审分支或 PR，就单独使用 **`/code-review`**。

### 上下文卫生（Context hygiene）

把第 1 至 3 步放在**同一个不间断的上下文窗口**中（在 `/to-tickets` 完成之前不要压缩或清空），让追问、规格说明和工单都建立在同一次思考之上。之后的每次 `/implement` 都从工单出发，全新开始。

这里的上限是**[高效区（smart zone）](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**：模型仍能保持敏锐推理的窗口（在最先进的模型上约为 150k 词元）。如果某个会话在 `/to-tickets` 之前就接近该上限，不要在能力退化后硬撑；在最近的阶段边界处执行 `/compact`，然后继续（见阶段边界一节）。

## 入口（On-ramps）

产生工作、随后汇入主流程的起始情形。

- **缺陷和需求不断堆积** → **`/triage`**。它让问题经过分诊（triage）角色处理，产出智能体可直接执行的问题，之后由 **`/implement`** 接手。

  分诊只处理**不是由你创建**的问题：缺陷报告、收到的功能请求、任何原始输入。`/to-tickets` 产出的工单已经是智能体可直接执行的，因此**不要对它们做分诊**。

- **有东西坏了** → **`/diagnosing-bugs`**。针对难啃的缺陷：一眼看不出原因的缺陷、间歇性失败、潜入两个已知良好状态之间的回归。它在拿到**紧反馈环（tight feedback loop）**之前拒绝推测（一条针对*这个*缺陷已经能变红的命令），然后用回归测试修复。如果真正的发现是没有合适的接缝（seam）能锁定该缺陷，它的事后复盘会交接给 **`/improve-codebase-architecture`**。

- **庞大而模糊的工作：全新项目或超大功能构建，一次会话装不下** → **`/wayfinder`**，这里认知要求最高的流程。当从当前位置到目的地（destination）的路线还看不清时，它会在问题跟踪器上绘制一张由**决策工单（decision ticket）**组成的**共享地图（shared map）**，逐个解决，产出**决策而非交付物**，直到驱散迷雾、路线清晰。在 **`/grill-with-docs`** 打磨的是能在一次会话中把握的想法的地方，wayfinder 面向的是装不下的想法；它更慢、密度更高，因此只用于这种情形，绝不用于范围清晰的功能。

  当地图清晰后，**它只做交接，不做构建**：在 **`/to-spec`** 处汇入主流程，由它把地图上相互关联的决策收拢为可构建的计划，再照常走 `/to-tickets` 和 `/implement`。把地图直接套进 `/implement` 会跳过这次收拢，把关联细节全部丢掉；只有当工作实际很小时，才直接进入 `/implement`。

## 代码库健康（Codebase health）

不是功能开发，只是日常维护。

- **`/improve-codebase-architecture`**：只要有空就可以运行，让代码库保持适合智能体工作的状态。它会呈现**加深机会（deepening opportunity）**；选中一个就*产生了一个想法*，可以带入主流程的 `/grill-with-docs`。它是发现候选的普查（survey）；而下文的 **`/codebase-design`** 是你设计选定方案的工作台。

## 底层的词汇（Vocabulary underneath）

两个模型调用（model-invoked）的参考技能，运行在其他技能*之下*，各自是其词汇的唯一可信来源。当问题出在**措辞**而非流程时，直接使用它们；也可以让上文技能按需引入它们。

- **`/domain-modeling`**：打磨项目的*领域*语言：质疑模糊术语，澄清一词多义（例如身兼三职的 "account"），把难以逆转的决策记为 ADR。它是 `/grill-with-docs` 驱动的积极实践，用来让 `CONTEXT.md` 保持为一份干净的术语表。
- **`/codebase-design`** 是深模块词汇（模块、接口、深度、接缝、适配器、杠杆、内聚），用于设计模块的*形态*：在干净的接缝上，用小接口承载大量行为。`/tdd` 和 `/improve-codebase-architecture` 都使用这套语言。

## 阶段边界（Phase boundaries）

一个**阶段（phase）**是会话中的一块工作：追问、实现、QA。在两个阶段之间的**边界**上，你有五个选项，而在它们之间抉择是整张地图中最模糊的决定：

- **Continue**：留在原地。不花成本，不丢东西。
- **`/clear`**：清空窗口，适用于这里的内容对后续毫无用处时。
- **`/handoff`** 写入一个可移植的 Markdown 文件。适用面窄：只用于**新的运行环境（harness）**、**新目录**、**同事**，或在**阶段中途**分叉出支线任务。它换来的是可移植性。
- **Subagent**：把范围明确的任务交给子智能体（subagent）的独立窗口，拿回一份报告。
- **`/compact`** 压缩当前上下文，并用它开启一个新会话。这是决策树底部的**默认选项**，而不是首选。

阅读 [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md) 了解有序决策树：五个问题、每个分支的理由，以及为什么一手来源（primary source）成本让 **Continue** 成为要最先排除的选项。在边界**处**做决定；在阶段中途，要么继续，要么把剩余工作拆给子智能体。

## 独立技能（Standalone）

完全独立于主流程。

- **`/grill-me`**：和 `/grill-with-docs` 同样犀利的追问，但是**无状态的（stateless）**：不在本地保存任何内容，也不构建 `CONTEXT.md`。当你**不在工作目录中工作**时使用它（打磨计划、设计、文稿，任何没有仓库托底的事情）。如果你身处工作目录，改用 `/grill-with-docs`：同样的追问，还留下书面记录，因此严格来说是更好的选择。
- **`/grilling`** 是追问原语本身：多轮（round）、前沿（frontier）、事实是智能体的任务、决策是你的任务。`/grill-me` 和 `/grill-with-docs` 是两个具名的入口，`/triage`、`/wayfinder` 和 `/improve-codebase-architecture` 都在内部运行它。只有当你想要不带任何包装的纯追问时，才直接使用它。
- **`/resolving-merge-conflicts`** 逐个代码块处理进行中的合并或变基冲突，按追溯到双方一手来源的**意图**解决，而不是挑行取舍，最后完成整个操作。它从不运行 `--abort`。独立于所有流程：当你已经身处冲突之中时使用它。
- **`/prototype`** 是一个小而一次性的程序，只回答一个设计问题：这个状态模型是否顺手，或者这个 UI 应该长什么样。一次性是对写法的约束，而不是销毁的承诺：答案会合入正式代码，原型本身作为**一手来源**保留在脱离 main 的 `prototype/<name>` 分支上，并从实现工单中指向它。它是主流程第 2 步中的绕道，但只要某个设计问题难以纸上解决，随时都可以用它。
- **`/research`**：把阅读的苦活委托给**后台智能体（background agent）**：它对照**一手来源**调查问题，然后在仓库中留下一份带引用的 Markdown 文件。你可以边等边继续工作。它产出的文件适合带*入*主流程的 `/grill-with-docs`，因为研究是为思考供料，而不是替代思考。
- **`/to-questionnaire`** 适用于卡住你的东西不在你脑中、也不在代码库中，而在**别人脑中**的情形，它会为对方写一份问卷（questionnaire）请其填写。它是 `/grill-me` 的反面：不是就主题追问你，而是就这次**发送**追问你（发给谁、要拿回什么），把问题对准信息缺口。收回的答复是 `/grill-with-docs` 或 `/to-spec` 的素材。
- **`/wizard`** 适用于只有**人类**能完成的步骤：置备基础设施、配置凭证或 CI 密钥、在不熟悉的第三方控制台上点选、执行一次性迁移或切换。它会生成可交互的 bash 脚本，逐个打开 URL、采集每个值，写入 `.env` 和 GitHub secrets，于是这套流程不再需要你每次都向智能体重讲一遍。它是模型调用的，智能体撞上只有你能通过的墙时就会拿起它。如果智能体自己能做，就该自己做；这里只用于人类必须参与（human-in-the-loop）的环节。
- **`/wait-what`** 是对没讲到位的那句话的补救。在任何其他技能的对话中途使用它，智能体会用你缺失的上下文、朴素的语言，借助 `CONTEXT.md` 的词汇，把刚说过的话重新讲一遍。它是事后补救；`/grill-with-docs` 是事前预防，因为提前约定好共享语言，才能从根本上避免行话出现。
- **`/teach`**：用多个会话学习一个概念，以当前目录作为有状态的工作区。
- **`/writing-for-agents`** 是为智能体写作消费型文档的参考：技能、AGENTS.md、被指向的文档。

## 前置条件（Precondition）

**`/setup-matt-pocock-skills`**：在运行第一个工程流程之前执行，用于配置其他技能所依赖的问题跟踪器、分诊标签和文档布局。也支持自定义问题跟踪器。
