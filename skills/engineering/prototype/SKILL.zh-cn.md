# 原型

原型是**为回答一个问题而写的一次性代码**。问题决定形态。

## 选择分支

根据用户提示、周围代码，或在用户在线时直接询问，判断要回答的是哪个问题：

- **“这个逻辑或状态模型是否合理？”** → [LOGIC.md](LOGIC.md)。构建单个可分享的 HTML 文件（自由试玩按钮加选项卡式引导走查），推动状态机走过那些在纸面上难以推理的用例，非开发人员也能上手操作。
- **“这个界面应该长什么样？”** → [UI.md](UI.md)。在单个路由上生成几个差异很大的 UI 变体，通过 URL 查询参数加悬浮底部栏切换。

两个分支的产物形态差异很大，选错会浪费整个原型。如果问题确实含糊且联系不上用户，就按周围代码默认选择更贴合的分支（后端模块选逻辑，页面或组件选 UI），并在原型顶部声明该假设。

## 两个分支通用的规则

1. **从第一天起就是一次性的，并且有明确标记。** 原型代码放在它所服务的模块或页面附近，让上下文一目了然，但命名要让偶然读到的人一眼看出这是原型，不是生产代码。一次性 UI 路由要遵守项目已有的路由约定，不要发明新的顶层结构。
2. **运行极其简单。** UI 原型从项目任务运行器的一条命令启动：`pnpm <name>`、`python <path>`、`bun <path>` 等。逻辑演示就是单个 HTML 文件，用户双击即可打开。无论哪种，都不需要动脑就能跑起来。
3. **默认不做持久化。** 状态放在内存里。持久化是原型要*验证*的东西，而不是原型应该依赖的东西。如果问题本身明确涉及数据库，就用临时库或本地文件，并取一个含义明确的“PROTOTYPE，用完即删”式名称。
4. **跳过打磨。** 不写测试，除了让原型*能跑起来*之外不做错误处理，不做抽象。目标是快速学到东西。
5. **把状态摆到台面上。** 每次操作后（逻辑分支）或每次切换变体时（UI 分支），打印或渲染出完整的有关状态，让用户看到发生了什么变化。
6. **完成后归档。** 把验证过的决策合入真实代码，然后把原型本身归档为**一手来源（primary source）**：提交到主分支之外的一次性分支，并在实现工单（issue）上留下指向该分支的上下文指针（context pointer）。答案也要归档（结论是什么，它回答了哪个问题），记在工单或提交信息里。主分支只保留验证过的决策。
