# 诊断缺陷（Diagnosing Bugs）

一套针对疑难缺陷的纪律。除非有明确理由，否则不要跳过任何阶段。

探索代码库时，阅读 `CONTEXT.md`（如存在），建立相关模块的清晰心智模型，并查看你触及范围内的 ADR。

## 脱敏（Redact）

本技能要求你展示命令、输出和捕获的产物。**先给每个密钥脱敏**：用 `<REDACTED>` 代替。把循环构建在环境变量之上，让凭证留在环境中，而不是出现在你的展示里。捕获的产物带有认证头：只引用承载信号的那几行。

如果脱敏后的输出不足以定位缺陷，直接说明，并向用户求助。

## 阶段 1：构建反馈环

**这就是本技能的全部。** 其余都是机械活。如果你有一个针对该缺陷的**紧**通过或失败信号（专治*这个*缺陷，一跑就变红），你一定能找到根因；二分、假设检验和插桩都只是消费它。如果你没有，再怎么盯着代码看也救不了你。

在这里花不成比例的精力。**主动，有创意，绝不放弃。**

### 构建反馈环的方法，大致按以下顺序尝试

1. 在能触及缺陷的接缝处写**失败测试**：单元、集成、端到端均可。
2. 对运行中的开发服务器发起 **Curl 或 HTTP 脚本**。
3. 用固定输入做 **CLI 调用**，把标准输出与已知良好的快照做 diff。
4. **无头浏览器脚本**（Playwright 或 Puppeteer），驱动 UI 并断言 DOM、控制台和网络。
5. **重放捕获的调用链。** 把真实的网络请求、载荷或事件日志存盘，隔离重放进相关代码路径。
6. **一次性测试架。** 拉起系统的最小子集（一个服务加模拟依赖），用一次函数调用走通缺陷路径。
7. **属性或模糊循环。** 如果缺陷是“有时输出错误”，跑 1000 个随机输入，观察失败模式。
8. **二分架。** 如果缺陷出现在两个已知状态（提交、数据集、版本）之间，把“在状态 X 启动、检查、重复”自动化，于是可以 `git bisect run`。
9. **差异循环。** 同一份输入分别跑旧版本和新版本（或两种配置），diff 输出。
10. **HITL bash 脚本。** 最后手段。如果必须有人点鼠标，就用 `scripts/hitl-loop.template.sh` 指挥*人类*，让循环仍有结构。捕获的输出回流给你。

选对反馈环，缺陷等于修好了 90%。

### 收紧循环

把循环当产品打磨。有了*一个*循环，就**收紧**它：

- 能否更快？（缓存准备工作，跳过无关初始化，缩小测试范围。）
- 信号能否更锐？（断言具体症状，而不是“没崩就算过”。）
- 能否更确定？（固定时间、固定随机种子、隔离文件系统、冻结网络。）

30 秒还 flaky 的循环约等于没有循环；2 秒且确定的循环才是紧的，才是调试超能力。

### 非确定性缺陷

目标不是干净复现，而是**更高的复现率**。把触发器循环 100 次，并行，加压，收窄时间窗，加 sleep。一个 50% 复现的 flake 可以调，1% 的不行；持续抬高复现率，直到可调试为止。

### 确实建不出循环时

停下来，明确说出来。列出你试过的方法。请用户提供：(a) 能复现问题的环境访问权限，(b) 脱敏后的捕获产物（HAR 文件、日志转储、core dump、带时间戳的录屏），或 (c) 允许添加临时的生产插桩。**没有**循环就不要进入推测阶段。

### 完成标准：变红的紧循环

当循环**又紧又能变红**，阶段 1 即完成：你能说出**一条命令**（脚本路径、测试调用、curl），你**已经实际运行过至少一次**（展示调用和输出，已脱敏），并且它满足：

- [ ] **能变红（Red-capable）**：它驱动真实的缺陷代码路径，并断言**用户描述的精确症状**，因此能在这个缺陷上变红、修好后变绿。不是“跑起来不报错”；它必须能*抓住这个具体缺陷*。
- [ ] **确定性（Deterministic）**：每次运行结论一致（flaky 缺陷：按上文固定为高复现率）。
- [ ] **快速（Fast）**：秒级，不是分钟级。
- [ ] **智能体可运行（Agent-runnable）**：你可以无人值守地运行；人类只通过 `scripts/hitl-loop.template.sh` 参与。

如果你发现自己在该命令存在之前就开始读代码建理论，**停下：跳过假设直奔结论，正是本技能要防止的失败。**没有能变红的命令，就不进入阶段 2。

## 阶段 2：复现加最小化

运行循环，看着它随缺陷出现而变红。

确认：

- [ ] 循环复现的是**用户**描述的失败模式，而不是附近恰好出现的另一种失败。修错缺陷等于白修。
- [ ] 失败可多次复现（非确定性缺陷：在足够高的复现率下可复现，便于调试）。
- [ ] 已捕获精确症状（报错信息、错误输出、变慢的耗时），以便后续阶段验证修复是否真的对症。

### 最小化

变红之后，把复现压缩到**仍能变红的最小场景**。输入、调用方、配置、数据、步骤，一次只砍一项，每砍一次重跑循环，只保留对失败起决定作用的部分。

为什么要做：最小复现能缩小阶段 3 的假设空间（剩下可怀疑的部件更少），还能成为阶段 5 中干净的回归测试。

当**每个剩余元素都起决定作用**，即完成：拿掉其中任何一个，循环就变绿。

复现**并**最小化都完成之前，不要继续。

## 阶段 3：提出假设

测试任何假设之前，先生成 **3 至 5 个排好序的假设**。单一假设会锚定在第一个看似合理的想法上。

每个假设必须**可证伪**：说出它做出的预测。

> 格式：“如果 <X> 是根因，那么 <改动 Y> 会让缺陷消失，或 <改动 Z> 会让它恶化。”

如果说不出预测，这个假设就是感觉：丢掉或打磨它。

**测试之前先把排序后的清单展示给用户。** 他们常有领域知识，能瞬间重排（“我们刚上线了针对第 3 条的改动”），或知道哪些假设已经排除过。廉价的检查点，巨大的时间节省。如果用户暂离（AFK），不要阻塞，按你的排序继续。

## 阶段 4：插桩验证

每个探针必须对应阶段 3 中的某个具体预测。**一次只改一个变量。**

工具偏好：

1. 环境支持时优先用**调试器或 REPL 检查**。一个断点胜过十行日志。
2. 在能区分假设的边界处打**针对性日志**。
3. 绝不“全量打日志再 grep”。

**每条调试日志打唯一前缀**，例如 `[DEBUG-a4f2]`。结尾清理时一次 grep 即可。无前缀的日志会残留；带前缀的日志会消亡。

**性能分支。** 性能回归通常不靠日志定位。而是：建立基线测量（计时架、`performance.now()`、剖析器、查询计划），然后二分。先测量，再修复。

## 阶段 5：修复加回归测试

先写回归测试**再修**，但前提是有**合适的接缝**。

合适的接缝是指测试在该处能练到**真实缺陷模式**在调用点出现的样子。如果唯一的接缝太浅（缺陷需要多个调用方，测试却只覆盖单个调用方；触发缺陷的调用链在单元测试里根本搭不出来），此处的回归测试只会带来虚假信心。

**如果没有合适的接缝，这本身就是结论。** 记下来。代码库架构正在阻止你锁定该缺陷。在下一阶段标出这一点。

如果有合适的接缝：

1. 把最小化复现转为该接缝处的失败测试。
2. 看着它失败。
3. 应用修复。
4. 看着它通过。
5. 用原始（未最小化）场景重跑阶段 1 的反馈环。

## 阶段 6：清理

声明完成之前必须满足：

- [ ] 原始复现不再复现（重跑阶段 1 的循环）
- [ ] 回归测试通过（或已记录无合适接缝）
- [ ] 所有 `[DEBUG-...]` 插桩已删除（grep 前缀确认）
- [ ] 一次性原型已删除（或移到明确标记的调试位置）
- [ ] 被证实的假设已写入提交或 PR 信息，让下一个调试者学到东西
