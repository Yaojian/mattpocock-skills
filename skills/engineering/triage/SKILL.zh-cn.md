# 分诊 (Triage)

将项目 issue 跟踪器上的 issue 推过一个由分诊角色组成的小型状态机。

如果本仓库把外部 pull request 视为一种需求来源（见 issue tracker 配置），分诊同样覆盖它们：**PR 就是附带代码的 issue**，使用同样的角色、同样的状态、同样的状态机，下面标有“对 PR 而言”的几处差异除外。单独的 `#42` 按跟踪器配置解析为 issue 或 PR。

分诊期间发布到 issue 跟踪器的每条评论或 issue **必须**以该声明开头：

```
> *This was generated by AI during triage.*
```

## 参考文档

- [AGENT-BRIEF.md](AGENT-BRIEF.md)：如何撰写持久耐用的智能体简报
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)：`.out-of-scope/` 知识库的工作方式

## 角色

两个**类别**角色：

- `bug`：有东西坏了
- `enhancement`：新功能或改进

五个**状态**角色：

- `needs-triage`：需要维护者评估
- `needs-info`：等待报告人提供更多信息
- `ready-for-agent`：已完整描述，无人值守 (AFK) 智能体可直接接手
- `ready-for-human`：需要人工实现
- `wontfix`：不处理

对 PR 而言，同样的状态对照附带代码来理解：`ready-for-agent` 表示已附上简报，智能体应该对 diff 采取下一步；`ready-for-human` 表示已可由人工合并。

每个经过分诊的 issue 应该恰好带有一个类别角色和一个状态角色。如果状态角色冲突，先标记出来，在做其他事之前询问维护者。

这些是标准 (canonical) 角色名。issue 跟踪器中实际使用的标签字符串可能不同，对应关系应该已经提供给你。如果没有，请用户运行 `/setup-matt-pocock-skills`。

状态流转：未打标签的 issue 通常先进入 `needs-triage`；再流转到 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。报告人回复后，`needs-info` 回到 `needs-triage`。维护者可随时覆盖；流转看起来不正常时，先标记出来并询问后再继续。

## 调用

维护者调用 `/triage` 并用自然语言描述需求。理解需求后行动。例如：

- “让我看看需要我关注的内容” ("Show me anything that needs my attention")
- “我们看下 #42” ("Let's look at #42")（issue 或 PR）
- “把 #42 移到 ready-for-agent” ("Move #42 to ready-for-agent")
- “有哪些智能体可以直接接手？” ("What's ready for agents to pick up?")

## 展示需要关注的内容

查询 issue 跟踪器，按时间从早到晚展示三个分组：

1. **Unlabeled**：从未分诊。
2. **`needs-triage`**：评估进行中。
3. **自上次分诊记录后报告人有新动态的 `needs-info`**：需要重新评估。

PR 在范围内时，在这些分组中包含外部 PR，并在每行标注 `[PR]` 或 `[issue]`。发现阶段只展示*外部* PR（跟踪器配置定义谁算外部人员），协作者正在开发的 PR 不属于分诊工作。该过滤仅用于发现阶段；明确点名的 PR 无论作者是谁都会处理。

展示数量和每条的一行摘要。让维护者挑选。

## 分诊某个具体的 issue 或 PR

1. **收集上下文。** 阅读完整的 issue 或 PR（正文、评论、标签、作者、日期；对 PR 还要读 diff）。解析之前的分诊记录，避免重复询问已解决的问题。用项目领域词汇表探索代码库，遵守相关区域的 ADR。对代码库做两项检查：(a) **冗余**：按领域概念（而不只是按请求的措辞）搜索是否已实现所请求的行为，并报告查找过哪里。如果找到了，就是已实现的 `wontfix`（见第 5 步）。(b) **历史拒绝**：阅读 `.out-of-scope/*.md`，找出与该请求相似的条目并展示出来。

2. **给出建议。** 告诉维护者你的类别和状态建议及理由，外加与该请求相关的代码库简述（包括是否已经实现）。等待指示。

3. **核实主张。** 在任何追问之前，先检查主张是否成立。对 bug，按报告人的步骤复现。对 PR，确认 diff 与声称一致：检出代码，运行相关测试或命令。报告结果：已确认（附代码路径）、复现失败，或细节不足（这是强烈的 `needs-info` 信号）。经过确认的核实会让智能体简报可靠得多。

4. **追问（如需）。** 如果请求需要进一步打磨，调用 Skill 工具两次，分别加载 "grilling" 和 "domain-modeling"，一轮一轮地追问成型，打磨领域术语，定下来的决策随手记进 `CONTEXT.md`/ADR。

5. **执行结果：**
   - `ready-for-agent`：发布智能体简报评论（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human`：与智能体简报结构相同，但注明为什么无法委派（需要判断力、需要外部访问、需要设计决策、需要手工测试）。
   - `needs-info`：发布分诊记录（模板见下）。
   - `wontfix` 则关闭 issue，评论内容取决于*原因*：
     - **已经实现**：该改动已存在于代码库。指出它的位置；**不要**写入 `.out-of-scope/`（该知识库只收*被拒绝*的请求，不收已构建的功能）。
     - **拒绝（bug）**：礼貌解释后关闭。
     - **拒绝（enhancement）**：写入 `.out-of-scope/`，在评论中链接它，然后关闭（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage`：打上角色。如有部分进展，可附一条评论。

## 快速状态覆盖

如果维护者说“把 #42 移到 ready-for-agent” ("move #42 to ready-for-agent")，信任他们，直接应用角色。先确认你要做什么（角色变更、评论、关闭），再行动。跳过追问。如果未经追问直接移到 `ready-for-agent`，询问他们是否要写一份智能体简报。

## Needs-info 模板

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

把追问中解决的所有事项记在 "established so far" 下，避免工作丢失。问题必须具体可执行，不能是 "please provide more info" 这类空话。

## 恢复之前的会话

如果 issue 或 PR 上已有分诊记录，先阅读它们，检查报告人是否回答了待解决的问题，更新整体情况后再继续。不要重复询问已解决的问题。
