# 改进代码库架构

发现架构摩擦，并提出**加深机会**：把浅模块重构为深模块。目标是可测试性和 AI 可导航性。

本命令基于项目的领域模型提供信息，并建立在共享的设计词汇之上：

- 通过 Skill 工具调用 "codebase-design"，获取架构词汇（**模块（module）**、**接口（interface）**、**深度（depth）**、**接缝（seam）**、**适配器（adapter）**、**杠杆（leverage）**、**内聚（locality）**）及其原则（删除测试，“接口即测试面”，“一个适配器等于假设性接缝，两个才是真实接缝”）。在每条建议中严格使用这些术语，不要偏移到 "component"、"service"、"API" 或 "boundary" 等说法。
- `CONTEXT.md` 中的领域语言为好的接缝命名；`docs/adr/` 中的 ADR 记录了本命令不应重新争论的决策。

## 流程

### 1. 探索

**先定范围再扫描：YAGNI。** 加深某个模块的回报在于让未来的相关修改更容易，因此要重点关注最近经常变化的代码部位。在查看之前先决定*去哪里*看：

- 如果用户指明了方向（某个模块、子系统、痛点），就接受该方向，并跳过下面的推断。
- 否则，回看一段足够长的提交历史（`git log --oneline`），找到代码库的热点，即反复出现的文件和区域，让这些路径优先吸引你的注意力。如果修改很分散，没有明显热点，就扩大扫描范围。

先阅读项目的领域术语表（`CONTEXT.md`）以及你所触及区域的相关 ADR。

然后派生一个子智能体（subagent）来走查代码库。不要遵循僵化的启发式规则；要有意识地探索，并记下你感受到摩擦的地方：

- 哪些地方理解一个概念需要在多个小模块之间来回跳转？
- 哪些模块是**浅**的，接口几乎和实现一样复杂？
- 哪些地方把纯函数抽出来只是为了可测试性，但真正的缺陷藏在调用方式中（没有**内聚**）？
- 哪些紧耦合的模块越过了各自的接缝互相泄漏？
- 代码库中哪些部分没有测试，或者很难通过现有接口测试？

对任何疑似浅层的东西应用**删除测试**：删除它会让复杂度集中，还是只会转移？“会集中”就是你想要的信号。

### 2. 以 HTML 报告呈现候选项

把自包含的 HTML 文件写入操作系统临时目录，不要落到仓库里。从 `$TMPDIR` 解析临时目录，回退到 `/tmp`（Windows 上为 `%TEMP%`），并写入 `<tmpdir>/architecture-review-<timestamp>.html`，让每次运行都有新文件。用系统命令为用户打开它（Linux 上为 `xdg-open <path>`，macOS 上为 `open <path>`，Windows 上为 `start <path>`），并告知用户绝对路径。

报告使用 **Tailwind via CDN** 做布局和样式，在适合用图表达结构时使用 **Mermaid via CDN** 绘制图表。Mermaid 与手写 CSS/SVG 可视化混用：关系呈图状时（调用图、依赖、序列）用 Mermaid，想要更具编辑感的呈现时（体量图、剖面、折叠动画）用手写的 div/SVG。每个候选项都要有**修改前后可视化**。要直观。

每个候选项渲染为一张卡片，包含：

- **文件**：涉及哪些文件或模块
- **问题**：当前架构为什么会造成摩擦
- **方案**：用简明英语描述会发生什么变化
- **收益**：用内聚和杠杆解释，并说明测试会如何改善
- **修改前后对比图**：并排、手绘，展示浅层现状和加深后的样子
- **推荐强度**：`Strong`、`Worth exploring`、`Speculative` 三者之一，以徽章形式渲染

报告结尾加上**首选推荐**小节：你会先做哪一个候选项，以及为什么。

**领域描述使用 CONTEXT.md 词汇，架构描述使用 `/codebase-design` 词汇。** 如果 `CONTEXT.md` 定义了 "Order"，就说 "Order 接收入口模块"，不要说 "FooBarHandler"，也不要说 "Order 服务"。

**ADR 冲突**：如果某个候选项与现有 ADR 矛盾，只有当摩擦真实到值得重议该 ADR 时才提出来。在卡片中明确标记（例如警告框：_"与 ADR-0007 矛盾，但值得重议，因为……"_)。不要列出 ADR 禁止的所有理论上的重构。

完整 HTML 脚手架、图表模式和样式指南见 [HTML-REPORT.md](HTML-REPORT.md)。

先不要提接口方案。文件写好后问用户：“你想深入探讨哪一个？”

### 3. 追问循环

用户选定候选项后，通过 Skill 工具调用 "grilling"，陪用户走完决策树：约束、依赖、加深后模块的形态、接缝之后是什么、哪些测试可以保留。

随着决策逐渐成形，副作用会内联发生；通过 Skill 工具调用 "domain-modeling"，让领域模型保持最新：

- **以 `CONTEXT.md` 中没有的概念为加深后的模块命名？** 把该术语加入 `CONTEXT.md`。如果文件不存在，就按需创建。
- **在对话中澄清了某个模糊术语？** 当场更新 `CONTEXT.md`。
- **用户以关键理由否决了候选项？** 提供撰写 ADR 的选项，表述为：_"要我把它记成 ADR 吗，这样以后的架构评审就不会重复提议它？"_ 只有当该理由确实是未来探索者避免重复提议所需要的，才提供；对临时性理由（“现在不值得做”）和显而易见的理由跳过。
- **想为加深后的模块探索备选接口？** 通过 Skill 工具调用 "codebase-design"，使用其中的双案并行子智能体模式。
