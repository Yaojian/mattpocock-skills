对照用户给定的固定点，评审 `HEAD` 与其之间的差异，走两个轴：

- **Standards**：代码是否符合本仓库已文档化的编码规范？
- **Spec**：代码是否忠实实现了来源问题或规格说明的要求？

两个轴以**并行的子智能体**运行，避免相互污染上下文，然后由本技能汇总发现。

问题跟踪器应当已经提供给你。如果缺失 `docs/agents/issue-tracker.md`，请告知用户运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 锁定固定点

用户所说的任何版本都可以作为固定点（提交 SHA、分支名、标签、`main`、`HEAD~5` 等）。如果用户没有指定，就请对方给出。

只采集一次差异命令：`git diff <fixed-point>...HEAD`（三点式，因此是对照合并基点的比较）。同时用 `git log <fixed-point>..HEAD --oneline` 记下提交列表。

继续之前，先确认固定点可解析（`git rev-parse <fixed-point>`）且差异非空。无效引用或空差异应当在这里失败，而不是在两个并行的子智能体内部失败。

### 2. 确定规格来源

按以下顺序寻找来源规格说明：

1. 提交信息中的问题引用（`#123`、`Closes #45`、GitLab 的 `!67` 等），按 `docs/agents/issue-tracker.md` 中的工作流拉取。
2. 用户作为参数传入的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支名或功能名匹配的规格文件。
4. 如果都找不到，向用户询问规格说明在哪里。如果用户说没有，**Spec** 子智能体跳过，并报告“无可用规格说明”。

### 3. 确定规范来源

仓库中记录代码写法的一切文档，例如 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`。

在仓库文档之上，Standards 轴永远携带下面的**坏味道基线（smell baseline）**：一组固定的 Fowler 代码坏味道（出自《重构》第 3 章），即使仓库没有任何文档也适用。两条规则约束它：

- **仓库优先。** 已文档化的仓库规范永远胜出；凡是规范认可、而基线会标记的写法，都压住不再报。
- **永远是判断，不是定罪。** 每种坏味道都是带标签的启发式提示（“疑似依恋情结”），绝不是硬性违规。和这里的任何规范一样，凡是工具链已强制的事项都跳过。

每种坏味道按“*是什么* → *怎么改*”阅读，对照差异逐条匹配：

- **Mysterious Name（命名之谜）**：函数、变量或类型的名字看不出它做什么或存什么。→ 改名；如果想不出诚实的名字，说明设计本身还含糊。
- **Duplicated Code（重复代码）**：同一逻辑形态在本次改动的多个代码块或文件中出现。→ 抽出公共形态，两处共同调用。
- **Feature Envy（依恋情结）**：一个方法访问另一个对象的数据胜过访问自己的数据。→ 把该方法搬到它羡慕的数据所在之处。
- **Data Clumps（数据泥团）**：同样的几个字段或参数总是一起出现（一个亟待诞生的类型）。→ 把它们打包成一个类型，整体传递。
- **Primitive Obsession（基本类型偏执）**：用基本类型或字符串代替本该拥有独立类型的领域概念。→ 给该概念一个小而专的类型。
- **Repeated Switches（重复的 switch）**：对同一类型的 `switch` 或 `if` 级联在改动中反复出现。→ 改用多态，或让两处共享同一个映射。
- **Shotgun Surgery（散弹式修改）**：一个逻辑改动迫使差异中多处文件跟着改。→ 把一起变化的东西收拢到一个模块中。
- **Divergent Change（发散式变化）**：一个文件或模块因几个互不相关的理由被改动。→ 拆分，让每个模块只因一个理由变化。
- **Speculative Generality（夸夸其谈的通用性）**：为规格说明中不存在的需求添加抽象、参数或钩子。→ 删掉；内联回去，直到真实需求出现。
- **Message Chains（消息链）**：长长的 `a.b().c().d()` 导航，调用方本不该依赖它。→ 在第一个对象上藏一个方法，把这段游走包起来。
- **Middle Man（中间人）**：一个类或函数大多只做转发。→ 砍掉它，直接调用真正的目标。
- **Refused Bequest（被拒绝的馈赠）**：子类或实现者忽略或重写了大部分继承来的东西。→ 放弃继承，改用组合。

### 4. 并行启动两个子智能体

**Standards 子智能体提示词**应包含：

- 完整的差异命令和提交列表。
- 你在第 3 步找到的规范来源文件列表，**加上第 3 步的坏味道基线全文**（子智能体没有其他途径拿到它）。
- 任务简述：“按文件或代码块报告：(a) 差异中违反已文档化规范的每一处：引用规范（文件加规则）；(b) 你发现的基线坏味道：说出名称并引用代码块。区分硬性违规和判断性提示：违反已文档化规范可以是硬性的，但基线坏味道永远是判断性提示，已文档化的仓库规范优先于基线。凡是工具链已强制的事项都跳过。400 词以内。”

**Spec 子智能体提示词**应包含：

- 差异命令和提交列表。
- 规格说明的路径或拉取到的内容。
- 任务简述：“报告：(a) 规格说明要求但缺失或只做了一半的需求；(b) 差异中超出要求的行为（范围蔓延）；(c) 看似已实现但实现疑似错误的需求。每条发现引用一行规格原文。400 词以内。”

如果缺失规格说明，跳过 Spec 子智能体，并在最终报告中注明。

### 5. 汇总

在 `## Standards` 和 `## Spec` 标题下分别呈现两份报告，原文呈现或轻微清理均可。**不要**合并或跨轴排序，因为两个轴刻意分离（见“为什么是两个轴”）。

结尾用一句话总结：每个轴的发现总数，以及*每个轴之内*最严重的问题（如有）。不要跨轴只挑一个最严重的问题：这种排序正是分离设计要防止的。

## 为什么是两个轴

一次改动可能通过一个轴、挂在另一个轴上：

- 代码遵守了所有规范，却实现了错误的东西 → **Standards 通过，Spec 不通过。**
- 代码完全按问题的要求做，却破坏了项目约定 → **Spec 通过，Standards 不通过。**

分开报告，才能防止一个轴掩盖另一个轴。
