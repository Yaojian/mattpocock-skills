## 功能简介

`resolving-merge-conflicts` 会逐个处理进行中的 git 合并 (merge) 或变基 (rebase) 操作中的每一个冲突块 (hunk)，然后运行项目自带的检查，最后以一次提交完成整个操作。

它拒绝把冲突当作纯文本问题来处理。在触碰任何冲突块之前，它会把冲突双方各自追溯到其**[主要来源 (primary source)](https://www.aihero.dev/ai-coding-dictionary/primary-source)**（提交信息、PR、原始 issue），因此它是在两种意图之间做选择，而不是在两段文本之间做选择，并且只要双方兼容就会同时保留。如果双方确实无法兼容，它会选择符合本次合并既定目标的一方，并写明取舍。它不会为了掩盖冲突而虚构任何新行为，`--abort` 也不是它的可选项：合并一定会被推进到完成的提交。

## 何时使用

输入 `/resolving-merge-conflicts` 即可调用；当任务符合条件时，[智能体 (agent)](https://www.aihero.dev/ai-coding-dictionary/agent)会自动选用它。

当 git 已经停在它自己无法解决的冲突上时，就该用它。它的范围只限于眼前的冲突，不涉及冲突两侧的其他内容：

| 你的处境 | 该用的技能 |
| --- | --- |
| 正在合并或变基，工作树中有冲突标记 | 就是本技能 |
| 合并已完成，但某些功能开始异常，且原因不明 | [diagnosing-bugs](https://aihero.dev/skills-diagnosing-bugs) |
| 规划如何切分工作，以减少分支碰撞 | 两者都不是：见下面的并行工作问题 |

## 主要来源优先于 `ours` 和 `theirs`

本技能要消灭的失败模式是按标志解决冲突：`--ours`、`--theirs`，或者随手删掉看起来不重要的那一块，只求标记消失、构建通过。这种解决方式在语法上可以完美无缺，却可能静默丢掉别人有意做出的修改。

没有读过的意图，你就无法保留它。因此工作从历史记录（提交、PR、[工单 (ticket)](https://www.aihero.dev/ai-coding-dictionary/ticket)）开始，然后才进入 diff。同理，循环中的另一步也是为此而设：技能会找到仓库自带的[自动化检查 (automated check)](https://www.aihero.dev/ai-coding-dictionary/automated-check)，并在提交前运行它们，因为合并是 git 中最容易产出“两边都沾一点、两边的测试都不通过”的代码的地方。

## 常见问题

**Claude Code 自己解决冲突已经很不错了，为什么还需要一个技能？**

增量价值在于“查找主要来源”和“运行反馈循环”这两个步骤，否则每次都要手工提示。没有提示的智能体通常只会根据 diff 给出一个看似合理的解决结果，然后就停了。本技能的价值在于它不允许智能体跳过的两个步骤：读懂每一方为何存在，以及事后运行检查。相比一个优秀的[模型 (model)](https://www.aihero.dev/ai-coding-dictionary/model)，这只是薄薄的一层增量，而这正是设计意图：已经有读者预测过，这整个技能会随着模型进步而变成空操作。

**为了从源头避免冲突，我应该让并行智能体避开相同文件吗？**

大体上不用。在并行任务之间划分文件禁区，成本大于收益，因为智能体已经足够擅长处理合并冲突，取舍并不像看起来那么严峻。唯一值得保留的纪律是先做大型重构。当十个分支已经从某次大型改名之前分叉出去之后，它再落地，这种情况的代价一直很高。

关于并行 worktree，有一条来自用户报告的注意事项：当兄弟[会话 (session)](https://www.aihero.dev/ai-coding-dictionary/session)各自在自己的工作树中构建工单时，合回来的合并最好由写下该改动的会话来执行，因为它已经知道改动的意图。把所有人的冲突批量丢给最后的一个智能体，恰好丢掉了本技能第 2 步必须去重建的[上下文 (context)](https://www.aihero.dev/ai-coding-dictionary/context)。

**为什么从不 `--abort`？**

中止会丢掉已经做完的解决工作，而下次重试时你会回到同一个冲突面前，情况毫无变化。本技能面向的是合并一定会发生的情况。如果你已经决定不该合并，那应该在调用之前做出决定，而不是作为循环内的一个分支。

## 生效标志

- 智能体在解决过程中向你引用提交信息、PR 或 issue，而不只是给你看 diff 冲突块。
- 每个冲突块都保留了双方的行为，或者附有明确说明，写清楚丢掉了什么以及为什么。
- 结果中没有出现两边分支都不存在的新内容。
- 在提交*之前*就已经找到并跑通类型检查、测试和格式化，而不是等发现坏了之后再补。
- 最终停在干净的工作树上，操作已完成，包括多提交变基中的每一个剩余提交。

## 在流程中的位置

一个随时可用的独立技能，不依赖其他任何技能：从 git 停滞时开始，到工作树干净且已提交时结束。它唯一真正的邻居是 [diagnosing-bugs](https://aihero.dev/skills-diagnosing-bugs)，接管的是合并干净完成但合并后代码行为异常的时点：那是诊断问题，不是冲突问题。它完全处在从想法到上线的 (idea-to-ship) 主流程之外，因此 [ask-matt](https://aihero.dev/skills-ask-matt) 是查看其前后步骤的地图。
