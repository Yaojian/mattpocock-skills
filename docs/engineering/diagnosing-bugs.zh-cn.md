## 功能简介

`diagnosing-bugs` 对疑难缺陷或性能回退跑六阶段诊断：建复现、最小化、假设排序、插桩、带回归测试修复、清理。

在**紧凑的**反馈环建成之前，它不许智能体形成任何理论：一个具名的命令，已经跑过一次，在*这个*缺陷上变红、修好后变绿。编码智能体拿到缺陷报告后的默认行为是读代码加猜测，这个技能拦住的就是这个。如果不存在能变红的命令，就没有第二阶段。这道门就是这个技能存在的意义。门后的事（对分、假设检验、插桩）一旦有了信号，都是机械活。

## 何时使用

输入 `/diagnosing-bugs`，任务匹配时智能体也会自动调用：它是模型可调用的，听到“diagnose”、“debug this”，或看到坏了、抛错、失败、变慢的报告就会触发。

把它留给硬骨头：第一眼看不穿的缺陷、偶发的 flaky、混进两个已知良好状态之间的回退。它刻意做得重，只想一句话问个答案的问题别用它。

| 你的处境 | 去哪里 |
| --- | --- |
| 能描述出症状的具体缺陷 | 用本技能 |
| 有明确前后对比的慢接口或耗时回退 | 用本技能：它有性能分支（先量基线，再对分） |
| “这个代码库哪里有瓶颈？”，没有具体症状 | 别用本技能。它诊断一个已知的失败，不做审计 |
| 别人抛过来的原始缺陷报告，还没确认、没写清楚 | 先走 [triage](https://aihero.dev/skills-triage) |
| 为回答设计问题写的抛弃型代码，不为追缺陷 | [prototype](https://aihero.dev/skills-prototype) |
| 按计划行为测试先行构建 | [tdd](https://aihero.dev/skills-tdd) |
| 根本没有好的接缝能锁住这个缺陷 | [improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture)：本技能自己就会交接到那里 |

## 紧凑循环就是这个技能

第一阶段花不成比例的力气，因为只有它难。技能给了一架搭循环的梯子，大致按推荐顺序排列：

1. 在能触及缺陷的接缝处写一个失败测试。
2. 对跑起来的开发服务器打 curl 或 HTTP 脚本。
3. 用固定输入调 CLI，把输出和已知良好的快照 diff。
4. 断言 DOM、控制台或网络的无头浏览器脚本。
5. 重放捕获：保存下来的请求、载荷或事件日志，在隔离环境里走一遍代码路径。
6. 抛弃型小 harness：只取系统的最小子集，一次函数调用。
7. 属性或 fuzz 循环，给“有时输出错”的问题用。
8. 能交给 `git bisect run` 的对分 harness。
9. 差异循环：同一输入，老版本对新版本。
10. [人在回路 (human-in-the-loop)](https://www.aihero.dev/ai-coding-dictionary/human-in-the-loop) bash 脚本，最后手段。技能自带 `scripts/hitl-loop.template.sh` 模板：智能体跑脚本，你在终端按提示操作，你的回答以可解析的输出返回。

目标不是*有个*循环。**紧凑**才是：快（秒级）、确定（每次结论一致）、准（断言你的精确症状，而不是“没崩”）、智能体可无人值守跑。30 秒还 flaky 的循环比没有好不了多少。对时有时无的缺陷，目标不是干净复现，而是**更高的复现率**：循环触发、并行、加压、注 sleep，一直把 flaky 率推到能调试为止。

真搭不出来时，技能要求它停下并明说，列出试过什么，然后向你要[环境 (environment)](https://www.aihero.dev/ai-coding-dictionary/environment)权限、捕获到的工件，或加临时插桩的许可。它不该硬着头皮去猜。

## 阶段之间的门

阶段是门，不是检查清单。每一道都要求某个具体条件成立才放行。

| 门 | 必须成立的条件 |
| --- | --- |
| 进入第二阶段 | 有一个具名命令，已经跑过并贴出输出，能在这个缺陷上变红 |
| 进入第三阶段 | 复现已建成*并*最小化：剩下的每个元素都不可或缺 |
| 进入第四阶段 | 有 3 到 5 个排序好的可证伪假设，每个写清预测，先给你看再测任何一个 |
| 进入第五阶段 | 探针一一对应某个预测，每次只动一个变量，所有调试日志都打 `[DEBUG-a4f2]` 风格的标签，清理时一次 grep 就够 |
| 完工 | 原复现不再复现，插桩清零，证实正确的假设写进提交信息 |

第五阶段有个逃生舱值得知道。回归测试在修之前写，但前提是有**合适的接缝**：测试按调用点出现的真实缺陷模式覆盖真实缺陷。如果唯一可用的接缝太浅，技能要求它明说，而不是写个给人虚假信心的测试。这种缺失本身就是发现，也是死后复盘时路由到 `improve-codebase-architecture` 的依据。

## 常见问题

**我只想问个快问题，它也触发。**
这是本技能被上报最多的问题，属实。在 GPT-5.6-Sol 上尤其明显，用户报告说只描述一下问题就触发了：“模型触发了相当正式的 diagnosing-bugs 技能，然后开始搭复现场景（经常搭个价值有限的 mock 场景），才给我回复或建议。回复延迟很大。”同一形状在[议题 #578](https://github.com/mattpocock/skills/issues/578) 里有四个人独立报告。公认的修法是先轻后重，问题真值得才升级到重的，但改动还没落地。该技能是按 Claude Code 的调用行为调的阈值；换到激活阈值更低的[模型 (model)](https://www.aihero.dev/ai-coding-dictionary/model)就会过触发。在修好之前，实用的办法是说清你要什么（“直接回答，别诊断”），或在你的[宿主框架 (harness)](https://www.aihero.dev/ai-coding-dictionary/harness)里关掉它的模型调用。

**我能指着代码库问性能问题都在哪吗？**
不能。它诊断一个你已经能点名的失败。它的性能分支是给有症状的回退用的（先建基线测量，再对分，先量后修），不是主动扫一遍。主动扫的技能[有人提过又关掉了](https://github.com/mattpocock/skills/issues/431)；目前没有管这个的技能。

**写修复之前它会停下来问我吗？**
不会。只有第三阶段有人检点：排序好的假设清单先给你看再测，你不在就按它自己的排序往下走。插桩和修复之间没有门，所以智能体可能在你同意根因之前就开始写代码了。[议题 #124](https://github.com/mattpocock/skills/issues/124) 要的就是这道门，还开着。想要的话，调用技能时就说。

**这个缺陷我已经跑过 `/triage` 了，是不是重复劳动？**
部分是，两个技能还都不认。用一位读者的话说：“Triage 的第 3 步本质上是 diagnosing-bugs 第一到二阶段的浅层有界版本，但两个文件都没提对方。” Triage 做有界的“这真是缺陷吗，表面在哪”一遍；本技能做彻底版。先跑 triage 不浪费（它的验证经常给出第一阶段的大半原材料），但要准备在这里完整重做一遍，也别指望有交叉引用告诉你这件事。

**它贴的复现输出会泄密吗？**
可能。技能要求智能体贴出调用和输出，还会索要 HAR 文件、日志 dump、core dump 之类的工件。这些都不做脱敏。[议题 #674](https://github.com/mattpocock/skills/issues/674) 提的正是这个（凭据、token、cookie、个人数据跟着聊天、议题或 PR 跑出去），建议加脱敏护栏。还开着，没实现。脱敏目前是你的活，特别是在输出发往公开场合之前。

**我的安全扫描器把它标成高风险。**
Snyk 会标，误报。它是全套技能里唯一自带可执行 shell 脚本的（`hitl-loop.template.sh`），附带运行它和 curl 开发服务器的指令。已发布的 `.sh` 加运行指令加出站 HTTP，足够触发静态扫描器。脚本本身 30 行左右，就是 `read -r -p` 等人输入的提示。扫描器评的是能力面，不是证实的漏洞。

**`/diagnose` 怎么没了？**
v1.0.0 改名为 `/diagnosing-bugs`。老名字已不存在。你手里凡是链了 `/diagnose` 的东西（封装技能、存下来的提示）都要更新。

## 怎样算生效

- 它先给你看命令和变红的输出，再给任何理论。理论先到，说明技能没跑起来。
- 它复现的是你报告的那个失败，而不是半路发现的邻近失败。
- 它先把复现缩到最小再猜，并能说清剩下每块为什么缺不得。
- 动手测之前，你先看到 3 到 5 个带排序的假设，每个都有可证伪的预测。
- 它加的每条调试日志都带 `[DEBUG-a4f2]` 这类标签，宣布完工时 grep 该标签是空的。
- 提交或 PR 信息写了哪个假设是对的。
- 锁不住测试时，它直说，而不是写个浅测试交差。

## 在整体中的位置

`diagnosing-bugs` 是随时取用的独立技能。东西坏了就进来，修复加回归测试落地就出去；不存状态，不需要前置配置。[ask-matt](https://aihero.dev/skills-ask-matt) 遇到“有东西坏了”就路由到这里。

两个邻居重要。[improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture) 接[交接 (handoff)](https://www.aihero.dev/ai-coding-dictionary/handoff)：当真正的发现是代码没有接缝能锁住缺陷时，修复落地后、信息最多时再交过去。[triage](https://aihero.dev/skills-triage) 在它上游，管别人抛过来的原始报告，做的是同前两阶段的浅层版本。
