## 它的作用

`prototype` 写的是**回答问题的抛弃型代码**：这个状态模型手感对吗，或者这个界面应该长什么样。问题先行，并决定之后一切的形状；回答错问题的原型，外表再好也是纯浪费。

抛弃型是对代码**写法**的约束，不是对销毁的承诺。没有测试，除了能跑起来之外不做错误处理，不做抽象，不做持久化，因为这些都帮不上你学到那唯一想学的东西。留下来的是答案，把它折进真正的代码；而原型本身停在 main 之外的分支上，作为“答案从何而来”的证据。

## 什么时候用它

输入 `/prototype`，或者[智能体 (agent)](https://www.aihero.dev/ai-coding-dictionary/agent)在任务合适时自动调用它。

当你撞上一个靠聊聊不定的问题时就用它：一个边界情况在脑子里装不下的状态机，一个要并排看到三个版本才能想象的界面。[追问 (grilling)](https://www.aihero.dev/ai-coding-dictionary/grilling)会话恰恰会在这类问题上膨胀：智能体换个说法，你靠猜，不确定性把范围撑大。停下追问，做一个抛弃型版本，看一眼，然后一句话作答。如果是有东西已经建好但行为不对、你想知道为什么，用 [diagnosing-bugs](https://aihero.dev/skills-diagnosing-bugs)；原型探索的是该建什么，而不是建好的东西为什么坏。

你也会在没主动选择时来到这里。[wayfinder](https://aihero.dev/skills-wayfinder) 会在地图上开 `prototype` 型决策[工单 (ticket)](https://www.aihero.dev/ai-coding-dictionary/ticket)，认领一张就是在用这个技能。

## 两个分支

问题决定分支，分支产出截然不同的产物：

- **“这个逻辑 / 状态模型手感对吗？”**：一个**可分享的单个 HTML 文件**。自包含的一页，不用构建也不用服务器，双击就能打开。它带一块每次点击后重渲染的带标签状态面板、按任意顺序点着玩的自由操作按钮，以及标签页式的**引导走查 (guided walkthrough)**（一个场景一个标签页，每个标签页下面是按顺序点的按钮）。一切都用领域语言标注，所以你可以把它交给设计师、PM 或领域专家，让他们亲自感受模型。页面背后的逻辑是一个干净的小纯模块（reducer、状态机或一组函数），和 DOM 解耦，验证过的版本可以直接提进真正的代码。
- **“它应该长什么样？”**：同一路由上的几个**差异巨大的** UI 变体，通过底部浮动栏和 `?variant=` URL 参数切换。变体必须在结构上互不认同，而不是颜色上；三个微调过的卡片网格是墙纸 (wallpaper)，不是原型。变体尽量渲染在真实页面里，对着真实数据和真实密度，因为放在真空中评判的变体永远都好看。

两者都把状态放内存，打开即用，每步之后都展示完整状态。当你发现自己在硬化它（加测试、接真实数据库、为以后可能要的情形做泛化）时，你已经不在做原型了。

## 原型是一手来源

做完的原型留下两样东西，去往不同地方。

**答案**（结论加它解决的问题）要持久记录：提交信息、ADR、实现 issue。主分支留的就是这个，把它折进真正的代码。

**原型**是答案从何而来的可运行证据，不删除。它也不属于 main：在那里没人维护，腐烂很快。所以它提交到 main 之外抛弃型的 `prototype/<name>` 分支，永不合并，并在实现 issue 上留一个指向该分支的[上下文指针 (context pointer)](https://www.aihero.dev/ai-coding-dictionary/context-pointer)。main 保持干净；探索过程对下一个接手的人依然可找、可重跑。

## 常见问题

**等等，原型不是应该删掉吗？**
现在不是了。以前是：做出来，留下答案，扔掉代码。对此最尖锐的反驳从来不是速度，而是*下个[会话 (session)](https://www.aihero.dev/ai-coding-dictionary/session)接手的人靠什么干活？*原型的文字总结丢掉的恰恰是让它令人信服的东西。所以原型现在被当作[一手来源 (primary source)](https://www.aihero.dev/ai-coding-dictionary/primary-source)：落在 main 之外的 `prototype/<name>` 分支，实现 issue 指向它。变的是代码住在哪里，不是纪律；它依然永不合入 main。

**以前能建终端应用，那个去哪了？**
逻辑分支现在产出可分享的单个 HTML 文件。终端应用只能由克隆了仓库、装好运行时的人驱动，而这恰恰把原型最需要意见的人排除在外：设计师、PM、知道状态模型本该是什么意思的领域专家。一个双击打开、能当邮件附件发出去的自包含文件，谁都能点。底下的纯逻辑模块没变，依然是能提进真正代码的那部分。

**有个智能体让我 `/prototype`，但我本该去实现。**
已知问题，是命名问题。`prototype` 是个通用又讨喜的词，在不懂流程的智能体读来，一旦工单存在它就是“显而易见的下一步”，所以即使设计已在对话里完全敲定，它也会按名字推荐。如果你已经知道要建什么，下一步是按工单 `/implement`。只有当某个具体设计问题确实没解决、且靠聊解决不了时，才来做原型。

**应该在构建任何生产功能之前先把整个应用做原型吗（比如拿给潜在客户演示）？**
那是披着这个技能名字的另一种产物。这里的原型只回答一个问题，而“整个应用是什么”不是一个问题。全应用原型没有自然的停止点，会靠惯性长成生产应用：清理那一遍永远不会发生，按原型规则写的代码（无测试、无错误处理）最终摆到用户面前。如果需要销售演示，就明确地当演示来做，并声明其中没有任何生产代码。如果要解决设计问题，就把它切到那个问题为止。

**怎么在独立会话里跑它？**
原型住在自己的目录里，会产生大量你不想带进提问线程的[上下文 (context)](https://www.aihero.dev/ai-coding-dictionary/context)，所以去别处跑，只把答案带回来。[handoff](https://aihero.dev/skills-handoff) 是双向的桥。

**这不是烧 token 最快的方式吗？**
可能，如果你把靠聊就能回答的问题拿来做原型，或者让一个原型蔓延到整个功能。真正该比的不是 token 和零，而是 [token](https://www.aihero.dev/ai-coding-dictionary/token) 和“错误的状态模型建完、有了生产调用方才发现”的代价。问题切窄，运行做短，花费就成比例。

## 生效的标志

- 你能一句话说清原型为回答哪个问题而存在，而且这句话写在演示顶部，不只在你脑子里。
- 不读代码的人能开逻辑演示。他们打开文件，按走查标签页点按钮，用自己的话描述看到的东西。
- 有人说“等等，这不应该出现”或“咦，我还以为是 X”。那是*想法*里的 bug，而这正是全部意义。
- UI 变体在布局和信息层级上互不认同，而不只是颜色和文案，反馈是“B 的头加 C 的侧边栏”。
- 一次坐下来就答完。如果做了一天还在做，问题太大，拆分它。
- 结束时，main 里只有决策、没有原型，实现 issue 指向还留着原型的分支。

## 它在流程中的位置

`prototype` 是**随时取用的独立技能**：你随时进入解决一个设计问题，再随时退出，同时它也是别的技能运转的机器。

它最大的消费者是 [wayfinder](https://aihero.dev/skills-wayfinder)。wayfinder 地图由**决策工单**组成，`prototype` 是工单四种类型之一，用于“应该长什么样”“应该怎么行为”这类靠讨论解决不了的阻塞问题。Wayfinder 用具体可反应的东西提高雾中讨论的清晰度，这个技能就是做出那个具体东西的方式。原型工单用答案来关闭，原型作为资产挂在地图上。

其他邻居在它的上游和下游。[grill-me](https://aihero.dev/skills-grill-me) 和 [grill-with-docs](https://aihero.dev/skills-grill-with-docs) 回答能追问的问题；问不出的来这里，答案用一句话带回访谈。下游是验证过的状态模型或 UI 方向，成为 [to-spec](https://aihero.dev/skills-to-spec) 的已确定输入，可以直接内联原型产出的富含决策的片段，而不用白话重述。其他情形，[ask-matt](https://aihero.dev/skills-ask-matt) 会带你走遍全套。
