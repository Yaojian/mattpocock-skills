## 它能做什么

`to-questionnaire` 把你独自拿不定的决策变成一份**问卷 (questionnaire)**：一份 Markdown 文档，交给掌握你所缺信息的那个关键人，由对方异步填写，或由你们俩在会议上一起过一遍。

它追问的是**发送 (send)**，而不是主题。围绕主题访谈你在这里没有意义：正因为不懂主题，你才要写信给别人。所以它只问你一定能回答的两件事（这封问卷发给谁，你希望拿回什么），文档中的每个问题都瞄准两者之间的**缺口 (gap)**。

## 何时使用

输入 `/to-questionnaire` 即可调用，[智能体 (agent)](https://www.aihero.dev/ai-coding-dictionary/agent)不会自行调用。

当决策卡在某一个人的头脑里时用它：客户、领域专家、掌握业务规则的高管、不在同一团队的同事。具体用哪个技能，取决于答案实际在哪里：

| 答案在…… | 用什么 |
| --- | --- |
| 你自己的头脑里，还没打磨 | [grill-me](https://aihero.dev/skills-grill-me) |
| 代码库里 | [grill-with-docs](https://aihero.dev/skills-grill-with-docs) |
| 别人头脑里 | `to-questionnaire` |
| 还没在任何人头脑里，需要先拿出东西来让人反应 | [prototype](https://aihero.dev/skills-prototype) |

常见情况是[追问 (grilling)](https://www.aihero.dev/ai-coding-dictionary/grilling)进行到一半卡住：浮现出来的有些问题不该由你回答。在同一段对话里跑 `/to-questionnaire`，把这些问题拿离线问，拿回答案再继续。

## 问的是发送，而不是主题

访谈只有两轮，问完即止。

- **发给谁？** 对方的角色、专长、和你的关系。这决定语气，也决定文档要带多少背景：外部客户需要铺垫，同事不需要。
- **你希望拿回什么？** 你独自解决不了的具体决策或事实。这就是成品文档的验收清单：你点名的每一项，都会对应文档中的问题。

之后全部是起草。文件落在当前目录的 `to-questionnaire-<slug>.md`。没有 setup，没有工作区，不需要配置。

## 文档长什么样

它被框定为一份**发现型问卷 (discovery questionnaire)**（你缺上下文，对方持有上下文），这个定位决定了它的形状：

- 开头一行写清它关乎哪个决策，再加一小段背景，给从没进过你脑子的收件人看。
- 问题按**最重要的优先 (most-important-first)** 排序，按主题分组，因为异步很可能只有一轮作答机会。
- 一题只问一件事，绝不复合，每个问题下面留作答位置，只在可能被误读的问题下加一句“为什么问这个”。
- 明确允许回答“不知道”：标出来的不确定性有用，读起来像事实的自信猜测有害。
- 结尾收网：还有我们没问到、但你觉得我们该知道的事吗？

它有意不做两件事。它不做**分支**：问题是扁平的分组列表，不会因为你选了 A 就跳过 D 部分。它也不做**多收件人**：一次运行只产出一份文档，给一个人。

## 常见问题

**它会读我的追问会话并从中提取问题吗？**
不会作为独立步骤。技能没有导入阶段：先问发送，再起草。它在追问之后好用的原因，是你在**同一段对话**里运行它，[会话 (session)](https://www.aihero.dev/ai-coding-dictionary/session)已经在[上下文 (context)](https://www.aihero.dev/ai-coding-dictionary/context)里，起草时可以直接取用。在全新会话里启动，它对之前的追问一无所知，回答“你希望拿回什么”时就得自己重新补主题。

**缺的答案不在同一个人手里，能按收件人拆分吗？**
不能。第一步要的是**那一个**收件人，单数，整份文档的语气和背景都按这个人调。如果三个人各掌握一部分答案，就跑三次，一人一份。有人提过在同一份文档里按专业或角色分发问题，这个需求存在，但发布版本不做。

**问题之间有依赖吗？会按前面的回答跳过某些部分吗？**
没有。依赖式问题设计讨论过，但没有发布。输出是静态文档：主题分组，最重要的优先，每个问题都有效。反对分支设计的理由很实在：[模型 (model)](https://www.aihero.dev/ai-coding-dictionary/model)要在真实答案之前规划两三个以上的问题，本来就规划不好，而分支文档要求在每个答案之前把所有问题都规划好。

**如果对方也不知道呢？**
文档会让对方直说。“不知道”和部分回答是被明确邀请的，标出来的不确定性比猜测值钱，因为模糊的回答和自信的错误回答一旦回到你的上下文里，看起来完全一样。

**它会发出去吗（Slack、议题跟踪、邮件）？**
不会。它只在当前目录写一个 Markdown 文件，并告诉你路径。投递归你：粘贴进[工单 (ticket)](https://www.aihero.dev/ai-coding-dictionary/ticket)、丢进 Slack 线程、作为邮件附件，或者共享屏幕现场一起过。这四种都有人手工做过。

**这不就是批量版的 `/grill-me` 吗？**
不是，这个区分值得守住。`grill-me` 本来就是**多轮 (rounds)**：一次问出整个前沿，再根据你的回答重新计算，所以“一次把问题全给我”的需求在那里已经满足。`to-questionnaire` 是另一个维度：不在于问题怎么交付，而在于答案在谁的头脑里。自己答得更快是 `grill-me` 的事，把答案从别人那里拿出来才是这个技能的事。

**不用技能，直接让智能体写不行吗？**
行，在它出现之前很多人就是这么做的：`OPEN_QUESTIONS.md` 文件、发给客户的表格、每个未答问题一张“需要更多信息”工单。技能带来两件事：访谈绝不飘到主题上，产出的文档形状是非技术收件人真正能填的。如果你已有管用的内部格式，实话是你不需要这个。

## 生效标志

- 它问收件人和你希望拿回什么，问完即止。问到主题本身，就是技能跑偏了。
- 你说的每项“希望拿回的东西”，都能在文件中找到对应的问题。
- 问题读起来是问**对方**知道的东西，而不是把你自己的开放问题原文抄下来。
- 没进过这段对话的人拿到文件，也知道为什么收到它、何时之前回复。
- 拿回的答案能作为新一轮追问的可用输入，而不是带来一批全新的问题。

## 它在整体中的位置

`to-questionnaire` 是随时可用的独立技能。它位于你自身知识的边界上，下一步是找人而不是找另一个技能，多数时候出现在流程中途，规划卡在不该由你决定的事情上。

它的邻居是 [grill-me](https://aihero.dev/skills-grill-me)，两者按答案在哪里分工：追问挖的是你，问卷挖的是别人。拿回的东西是原材料：喂给下一轮追问，或者在要进入构建时喂给 [grill-with-docs](https://aihero.dev/skills-grill-with-docs) 或 [to-spec](https://aihero.dev/skills-to-spec)。当你不确定当下适合哪个技能时，[ask-matt](https://aihero.dev/skills-ask-matt) 会帮你分发。
